# Implementation Goal Orchestration

An implementation goal stays with the orchestrator, who remains the default user conversation and owns design decisions with the user, every governing design artifact, the coordination root, integration gates, disposition, acceptance, and the final report; plans come from Main's `plan-implementation` run (step 2). It never authors or repairs a plan.

## Execution Responsibility

Use the current goal context or applicable handoff and the next phase's existing input/result contract. For each started PR node, MUST load `manage-agents` to assign or resume that PR's persistent implementation 🐒 Sidekick and return its responsibility, continuity, assignment boundary, node and base, prerequisites, exact execution root, and user-conversation route. The orchestrator keeps the coordination root plus every execution root as `orchestrator`; each Sidekick joins only its execution root as `implementer`. At commission, apply and verify the `manage-agents` `<emoji> <role> · <purpose>` title, or report the title capability gap. Seats describe thread participation rather than authority; `manage-agents` owns the complete role-to-seat mapping.

For agent-router delivery, use `agent-collaboration`; roots are linked through existing message references rather than a new hierarchy mechanism.

## Orient the Goal

1. Classify `general-domain | runtime-skill-package`. A runtime skill package requires the exact accepted `skills-creation` composition for this named run. If the composition is absent, stale, or mismatched, route to `skills-creation` and stop before product delivery.
2. Establish `requested terminal: plan-only | pr-ready-unmerged`; default to `pr-ready-unmerged` unless the user supplied a narrower terminal, and carry that terminal in the `ready-for-planning` payload so the planner receives it from its caller. Merge is a separately authorized extension through `implementation-pr-wrapup`, never an inferred terminal.
3. MUST invoke `practices-show-me-your-work` and return the shared work reference (or explicitly unshared checkpoint path) plus responsibility for the whole work or a contribution. Reuse supplied work context for nested work. The tracker owns continuity, fallback, conditional views, and deliberate thread resolution.
4. MUST load `references/goal-contract-and-routing.md` and return the current orientation, admitted breakdown and PR plans, next owner or exact stop, and finish decision.
5. Read current repository instructions, relevant source and diff, governing artifacts, breakdown, plans, proof, and review evidence. Use the trail to find evidence, then verify current facts at their source; a historical result is context, not current proof.
6. MUST load `../../shared-references/phase-return-tokens.md` and map a returned token to its next owner: `requirements-gap` -> `discuss-pathfinding`; `specification-gap` or `program-design-gap` -> `orchestrator-design`; `ready-for-planning` and `plan-defect` -> Main, as that file says; `ready-for-implementation` -> `implement-plan` inside that PR's assignment; `ready-for-review` -> `implementation-review` for `general-domain` or the `skills-creation` implementation-review stage for `runtime-skill-package`. Mapping names the next owner; it never widens the requested task or terminal.

## Carry the Delivery Loop

1. Decide reversible, in-scope calls yourself and record each as a decision through `practices-show-me-your-work` instead of asking; ask only when the call would change a public contract, persisted data format, or ownership. The implementation 🐒 Sidekick handles implementation choices and executes its assignment. If implementation meaning is incomplete, it returns the exact material design/plan question, evidence, recommendation, and blocked consequence to the orchestrator, keeps the goal open, and resumes after the decision; the orchestrator invokes `orchestrator-design` when governing design meaning must change.
2. Admit either current reviewed design or an evidence-backed repository improvement accepted by `plan-improve-repo`, through its ready breakdown. Without a ready breakdown, or a ready plan for an executable node, end this run with `ready-for-planning`; do not load a planner here. Add no second plan review. A ready `plan-only` result reaches that requested terminal; a ready breakdown with a ready delivery plan continues immediately.
3. Start executable nodes in the breakdown's order. Independent PRs run in parallel on separate branches or worktrees, one writer per branch. A stack runs through `gh stack` from its lowest layer up: the orchestrator sequences the layers and commissions each as a one-PR assignment once its parent has a head and its plan is ready; the next layer may reuse the same Sidekick session with a new one-PR assignment. A node that waits for a contract node or an unmerged prerequisite stays pending. If implementation or fitting proof is incomplete, the Sidekick invokes `implement-plan` for its PR. It reports meaningful blockers and returns a concise source-and-proof receipt when its PR is ready for Main assessment.
4. When a PR's planned development and fitting proof are complete, the orchestrator assesses that PR before its independent review. Assess its current diff and actual proof against the accepted need, design, plan, node, base, and scope. Cross-PR interaction is proved at the breakdown's integration gates (step 9), not in this per-PR assessment. Unproven work returns to the responsible implementer for fresh affected proof. A mental-model break, public-contract change, owner decision, or plan defect stops dependent work and returns to its semantic owner. IF an implementer or reviewer reports a design break, load `../../shared-references/owner-decision-brief.md` and return the brief. Only a source-backed accepted assessment commissions the 🔎 Review Sidekick for its review scope (`implementation-review`) through `manage-agents`, using its verified `<emoji> <role> · <purpose>` title or reporting the title capability gap.
5. The 🔎 Review Sidekick runs `implementation-review` for general-domain work or the `skills-creation` implementation-review stage for a composed runtime skill package. It owns detailed source reading, lane reduction, and its review result. The orchestrator checks findings against cited evidence, resolves scope or design disputes, and returns accepted implementation corrections to that PR's implementer.
6. Main hands the corrected code and fresh affected proof to the same 🔎 Review Sidekick for that review scope, which checks them; the implementer does not contact the reviewer directly. It refreshes affected coverage and applies the convergence rule in `implementation-review`'s `references/finding-and-reduction.md`. Contextual design feedback remains separate from independent review.
7. Repeat correction, proof, and review while accepted findings remain. IF the review returns `not-converging`, load `../../shared-references/owner-decision-brief.md` and return a brief of what keeps failing and why.
8. When a PR's review is ready, assign `implementation-pr-wrapup` for that PR to an 🔧 Operator or its assigned implementation Sidekick. Operators own separately assigned Git, PR, and blocking-watch routines; wait for their notifications or authorized wakes through `manage-agents`, never by model polling. Stop at PR-ready and unmerged by default. Pass through explicit merge authority only after readiness.
9. After the PRs an integration gate names are PR-ready, Main runs that gate's proof and records in the trace the exact PR heads it tested together. A change the gate discovers routes through Main to the affected PR's Sidekick and reviewer. Per-PR readiness is never reported as delivery readiness before the named gates pass.

Record consequential decisions, accepted or rejected findings, corrections, proof outcomes, gate results, any missing-history baseline, blockers, and terminal results through `practices-show-me-your-work`. Keep logging a companion to delivery: do not create another lifecycle ledger, copied receipt store, counter protocol, or result replay mechanism.

## Boundaries and Finish

- Each Review Sidekick owns independent review findings and coverage for its review scope. The user owns material design decisions and phase gates. PR wrap-up owns PR gate inspection.
- Verify producer results proportionally. Current scope, source, outcome, evidence, and applicable stop conditions matter; a missing label alone does not invalidate a clear result. Require exact identity when it changes correctness, including the breakdown, node, base, canonical plan, reviewed diff or PR head, and source-bound proof.
- Shared work updates follow the tracker within task authority. Other external tracking remains separately authorized work and proves no delivery gate.
- On every terminal response, record the actual `complete | partial | blocked | stopped` outcome and continuation context through the tracker. Nested agents checkpoint without resolving the outer thread. Only the responsible whole-work agent checks current history and whole-work completion before resolution; render a view when requested or substantial synthesis is needed.

Open stand-ins keep a PR from `pr-ready` unless the owner accepts them, and the final report lists every open stand-in as unverified.

Completion: every material phase required by the requested terminal is currently verified (for `plan-only`, a ready breakdown and plans; for `pr-ready-unmerged`, admitted plans, implementation with fitting proof for every PR, a ready review for every review scope with accepted corrections, PR readiness for every PR, and every named integration gate passed on recorded heads), or the response names the exact decision or blocker. No phase boundary, missing label, logging failure, implied merge, or continuing after `not-converging` silently changes that result.
