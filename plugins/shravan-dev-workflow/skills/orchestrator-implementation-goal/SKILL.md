# Implementation Goal Orchestration

An implementation goal stays with the orchestrator, who remains the default user conversation and owns design decisions with the user, every governing design and implementation-plan artifact, the coordination root, cross-PR integration, disposition, acceptance, and the final report. After a main-authored plan is ready, one persistent implementation Sidekick owns each useful planned PR assignment's implementation, associated proof, and corrections. The user may explicitly choose direct contact with that assigned Sidekick inside its scope without changing execution ownership or governing authority. An independent persistent review Sidekick examines implementation only after the orchestrator has assessed completed development and proof.

## Execution Responsibility

Before planning, use the current goal context or applicable handoff and the next phase's existing input/result contract. The orchestrator loads `plan-implementation` itself and authors the plan. Only after that plan identifies useful PR assignments, MUST load `manage-agents` to assign or resume the corresponding persistent implementation Sidekicks and return each responsibility, continuity, assignment boundary, prerequisite, exact execution root, and user-conversation route. Main remains the default conversation unless the user explicitly chooses direct contact with an assigned Sidekick. The orchestrator keeps the coordination root plus every execution root as `orchestrator`; each Sidekick joins only its execution root as `implementer`. Seats describe thread participation rather than authority; `manage-agents` owns the complete role-to-seat mapping.

Each implementation Sidekick executes its assigned change and associated proof directly by default. It may select bounded native Workers only for independent work, needed expertise, or large disposable output whose benefit exceeds briefing, coordination, and verification cost; standalone prescribed procedures use native Operators. Do not add a supervisor solely to relay child output, and do not dispatch an Operator for tests that are coupled to the implementation. For Router delivery, use `agent-collaboration`; roots are linked through existing message references rather than a new hierarchy mechanism.

## Orient the Goal

1. Classify `general-domain | runtime-skill-package`. A runtime skill package requires the exact accepted `skills-creation` composition for this named run. If the composition is absent, stale, or mismatched, route to `skills-creation` and stop before product delivery.
2. Establish `requested terminal: plan-only | pr-ready-unmerged`; default to `pr-ready-unmerged`. Merge is a separately authorized extension through `implementation-pr-wrapup`, never an inferred terminal.
3. MUST invoke `track-show-me-your-work` and return the shared work reference (or explicitly unshared checkpoint path) plus responsibility for the whole work or a contribution. Reuse supplied work context for nested work. The tracker owns continuity, fallback, conditional views, and deliberate thread resolution.
4. MUST load `references/goal-contract-and-routing.md` and return the current orientation, admitted basis, next owner or exact stop, and finish decision.
5. Read current repository instructions, relevant source and diff, governing artifacts, plan, proof, and review evidence. Use the trail to find evidence, then verify current facts at their source; a historical result is context, not current proof.

## Carry the Delivery Loop

1. Main remains the default user conversation. The user may explicitly choose direct contact with an assigned implementation Sidekick inside its scope. In either branch, the Sidekick handles implementation choices and executes its assignment directly. If implementation meaning is incomplete, it returns the exact material design/plan question, evidence, recommendation, and blocked consequence to the orchestrator, keeps the goal open, and resumes after the decision; the orchestrator invokes `orchestrator-design` when governing design meaning must change. Main does not relay every internal progress turn or poll merely to keep the conversation active, and returning to Main for conversation does not pause authorized implementation.
2. Admit either current reviewed design or an evidence-backed repository improvement accepted by `plan-improve-repo`. If no current ready delivery plan exists, the orchestrator loads `plan-implementation` and authors it from settled design or the admitted finding. Helpers may return repository/proof evidence only. A ready `plan-only` result reaches that requested terminal; a ready delivery plan continues immediately.
3. Commission one implementation Sidekick per useful planned PR assignment without automatically moving the user's conversation away from Main. Record real prerequisites and write collisions from the plan. Independent assignments may run concurrently on separate execution roots; dependent assignments wait until the orchestrator verifies their prerequisites. If implementation or fitting proof is incomplete, each Sidekick invokes `implement-plan` for its assigned scope and executes directly by default, using only delegation justified under `manage-agents`. It reports meaningful blockers and returns a concise source-and-proof receipt when the assignment is ready for Main assessment; it does not send every internal progress turn through the orchestrator. Direct Sidekick contact remains available when the user explicitly chooses it. A milestone, completed slice, or phase return is a checkpoint.
4. When planned development and fitting proof are complete, the orchestrator performs the main assessment before any independent implementation review. Inspect the current diff and actual proof against the original need, accepted design, plan, PR scopes, and cross-PR integration. Confirm required behavior is demonstrated through the right observation seams, no required work or proof is missing, boundaries and names match the design, and unnecessary complexity or unplanned compatibility machinery was not introduced. Unproven work returns to the responsible implementer for fresh affected proof. A mental-model break, public-contract change, owner decision, or plan defect stops dependent work and returns to its semantic owner. Only a source-backed accepted assessment commissions the persistent independent implementation-review Sidekick through `manage-agents`.

   Return a concise source-backed assessment decision that makes the substantive inspection and outcome clear without imposing a reporting schema. A missing label alone does not invalidate adequate evidence; an assessment supported only by the implementer's summary does not authorize review.
5. The review Sidekick runs `implementation-review` for general-domain work or the `skills-creation` implementation-review stage for a composed runtime skill package. It owns detailed source reading, lane reduction, and its review result. The orchestrator checks findings against cited evidence, resolves scope or design disputes, and returns accepted implementation corrections to the implementer.
6. The same review Sidekick checks corrected code and fresh affected proof. It refreshes affected coverage and preserves the existing remediation limit. Contextual design feedback remains separate from independent review.
7. Repeat correction, proof, and review while accepted findings remain and fewer than three implementation-remediation passes have completed. After remediation three, stop `remediation-limit-reached` before review or remediation four unless the user explicitly authorizes continuation.
8. When review is ready, invoke `implementation-pr-wrapup` for the PR gates. Operators own standalone Git, PR, and blocking-watch routines; wait for their notifications or authorized wakes through `manage-agents`, never by model polling. Stop at PR-ready and unmerged by default. Pass through explicit merge authority only after readiness.

Record consequential decisions, accepted or rejected findings, corrections, proof outcomes, recovery use, blockers, and terminal results through `track-show-me-your-work`. Keep logging a companion to delivery: do not create another lifecycle ledger, copied receipt store, counter protocol, or result replay mechanism.

## Bounded Recovery

If current evidence shows that implementation review never occurred, invoke the ordinary first review. If prior implementation-review history should exist but its evidence is unavailable, inspect the current source and proof boundary and record what is missing and why another review is necessary. Admit exactly one recovery review by passing that explicit recovery authorization to `implementation-review` when no prior recovery is known and the normal allowance is not known exhausted. Preserve an unknown remediation count as unknown: never turn it into zero, reset a known count, or repeat recovery.

If the recovery review finds problems and a safe remaining correction budget cannot be established, report the findings and ask the user before correction. Known three-remediation exhaustion, known prior recovery, stale source/proof, unclear meaning, or unavailable required proof remains a stop.

## Boundaries and Finish

- The orchestrator remains the default user conversation and owns governing design and plan authorship, planning strategy, dependencies, PR grouping, cross-PR integration, main assessment, acceptance, source-backed disposition, routing, and the delivery terminal. Each implementation Sidekick directly owns bounded implementation, fitting proof, corrections, and routine mechanics for its main-planned assignment; the user may explicitly choose direct contact with it inside that scope. The review Sidekick owns independent review findings and coverage. The user owns material design decisions and phase gates. PR wrap-up owns PR gate inspection.
- Verify producer results proportionally. Current scope, source, outcome, evidence, and applicable stop conditions matter; a missing label alone does not invalidate a clear result. Require exact identity when it changes correctness, including the canonical plan, reviewed diff or PR head, and source-bound proof.
- Shared work updates follow the tracker within task authority. Other external tracking remains separately authorized work and proves no delivery gate.
- On every terminal response, record the actual `complete | partial | blocked | stopped` outcome and continuation context through the tracker. Nested agents checkpoint without resolving the outer thread. Only the responsible whole-work agent checks current history and whole-work completion before resolution; render a view when requested or substantial synthesis is needed.

Completion: every material phase required by the requested terminal is currently verified—planning for `plan-only`; planning, implementation with fitting proof, bounded independent review and accepted corrections, and PR readiness for `pr-ready-unmerged`—or the response names the exact decision or blocker. No phase boundary, missing label, logging failure, implied merge, repeated recovery, or fourth remediation silently changes that result.
