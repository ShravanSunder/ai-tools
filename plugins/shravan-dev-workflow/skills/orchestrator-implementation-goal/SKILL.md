# Implementation Goal Orchestration

An implementation goal stays with the orchestrator, who remains the default user conversation and owns design decisions with the user, every governing design artifact, the breakdown and every PR plan, the coordination root, integration gates, disposition, acceptance, and the final report. Planning happens before this skill runs: Main writes the breakdown and each PR's plan with `plan-implementation` in its own session. This skill admits a ready breakdown and the ready plan for each PR it starts, then runs execution, review, and wrap-up. It never authors or repairs a plan. After a PR's plan is ready, one persistent implementation 🐒 Sidekick owns that one PR's implementation, associated proof, and corrections; a Sidekick's assignment and horizon is one PR. The orchestrator sequences a stack's layers and commissions each layer as its own one-PR assignment. The user may explicitly choose direct contact with an assigned Sidekick inside its scope without changing execution ownership or governing authority. Main assesses each PR before an independent persistent Review Sidekick examines it.

## Execution Responsibility

Use the current goal context or applicable handoff and the next phase's existing input/result contract. Admit the ready breakdown and the ready plan of each PR node you start under `../../shared-references/canonical-implementation-plan.md`. When the breakdown is missing, or a node's base now exists but its plan does not, return `ready-for-planning` to Main with the admitted basis and, for a later frontier, the breakdown identity and node id. Main resolves it in its own session, outside this skill, and returns here with the ready records. For each started PR node, MUST load `manage-agents` to assign or resume that PR's persistent implementation 🐒 Sidekick and return its responsibility, continuity, assignment boundary, node and base, prerequisites, exact execution root, and user-conversation route. The next layer of a stack may reuse the same Sidekick session with a new one-PR assignment. Main remains the default conversation unless the user explicitly chooses direct contact with an assigned Sidekick. The orchestrator keeps the coordination root plus every execution root as `orchestrator`; each Sidekick joins only its execution root as `implementer`. At commission, apply and verify the `manage-agents` `<emoji> <role> · <purpose>` title, or report the title capability gap. Seats describe thread participation rather than authority; `manage-agents` owns the complete role-to-seat mapping.

Each implementation 🐒 Sidekick's tier, and what it executes itself, follow the staffing table in `manage-agents` (`../manage-agents/SKILL.md`, Commission an implementation 🐒 Sidekick), read from its PR plan's slice executor records: a Luna Sidekick executes an all-Workhorse PR directly, and a Daily-driver Sidekick executes its own and coupled slices and dispatches only plan-marked independent Workhorse slices to Luna 🛠️ Workers when the benefit test holds. Standalone prescribed procedures use 🔧 Operators. A Workhorse slice that stops at its boundary returns to Main as a plan defect; Main re-slices or re-tags it with a reason through the originating planner, and nobody silently re-runs it on a bigger model. Do not add a supervisor solely to relay child output, and do not dispatch an Operator for tests that are coupled to the implementation. For agent-router delivery, use `agent-collaboration`; roots are linked through existing message references rather than a new hierarchy mechanism.

## Orient the Goal

1. Classify `general-domain | runtime-skill-package`. A runtime skill package requires the exact accepted `skills-creation` composition for this named run. If the composition is absent, stale, or mismatched, route to `skills-creation` and stop before product delivery.
2. Establish `requested terminal: plan-only | pr-ready-unmerged`; default to `pr-ready-unmerged` unless the user supplied a narrower terminal, and carry that terminal in the `ready-for-planning` payload so the planner receives it from its caller. Merge is a separately authorized extension through `implementation-pr-wrapup`, never an inferred terminal.
3. MUST invoke `practices-show-me-your-work` and return the shared work reference (or explicitly unshared checkpoint path) plus responsibility for the whole work or a contribution. Reuse supplied work context for nested work. The tracker owns continuity, fallback, conditional views, and deliberate thread resolution.
4. MUST load `references/goal-contract-and-routing.md` and return the current orientation, admitted breakdown and PR plans, next owner or exact stop, and finish decision.
5. Read current repository instructions, relevant source and diff, governing artifacts, breakdown, plans, proof, and review evidence. Use the trail to find evidence, then verify current facts at their source; a historical result is context, not current proof.
6. MUST load `../../shared-references/phase-return-tokens.md` and map a returned token to its next owner: `requirements-gap` -> `discuss-pathfinding`; `specification-gap` or `program-design-gap` -> `orchestrator-design`; `ready-for-planning` -> Main, which resolves it by the admitted basis (normally `plan-implementation`) in its own session outside this skill; `plan-defect` -> Main, which resolves it through the plan's recorded `originating planner` (`plan-implementation | plan-improve-repo`) in its own session while PRs the defect does not touch continue; `ready-for-implementation` -> `implement-plan` inside that PR's assignment; `ready-for-review` -> `implementation-review` for `general-domain` or the `skills-creation` implementation-review stage for `runtime-skill-package`. Mapping names the next owner; it never widens the requested task or terminal.

## Carry the Delivery Loop

1. Decide reversible, in-scope calls yourself and record each as a decision through `practices-show-me-your-work` instead of asking; ask only when the call would change a public contract, persisted data format, or ownership. Main remains the default user conversation. The user may explicitly choose direct contact with an assigned implementation 🐒 Sidekick inside its scope. In either branch, the Sidekick handles implementation choices and executes its assignment under the staffing table. If implementation meaning is incomplete, it returns the exact material design/plan question, evidence, recommendation, and blocked consequence to the orchestrator, keeps the goal open, and resumes after the decision; the orchestrator invokes `orchestrator-design` when governing design meaning must change. Main does not relay every internal progress turn or poll merely to keep the conversation active, and returning to Main for conversation does not pause authorized implementation.
2. Admit either current reviewed design or an evidence-backed repository improvement accepted by `plan-improve-repo`, through its ready breakdown. Without a ready breakdown and the plans for the first frontier, return `ready-for-planning` to Main and stop this run; do not load a planner here. `plan-implementation` reviews each full plan before returning `ready`, so the orchestrator consumes that ready result and adds no second plan review. A ready `plan-only` result reaches that requested terminal; a ready breakdown with a ready delivery plan continues immediately.
3. Start executable nodes in the breakdown's order, riskiest unknown first. Independent PRs run in parallel on separate branches or worktrees, one writer per branch. A stack runs through `gh stack` from its lowest layer up: the orchestrator sequences the layers and commissions each as a one-PR assignment once its parent has a head and its plan is ready. A node that waits for a contract node or an unmerged prerequisite stays pending. Commission one implementation 🐒 Sidekick per started PR without automatically moving the user's conversation away from Main, and pick its tier from that PR plan's slice executor records with the staffing table in `manage-agents` (`../manage-agents/SKILL.md`, Commission an implementation 🐒 Sidekick). If implementation or fitting proof is incomplete, the Sidekick invokes `implement-plan` for its PR and executes or dispatches each slice as the staffing table and the slice's executor record say. It reports meaningful blockers and returns a concise source-and-proof receipt when its PR is ready for Main assessment; it does not send every internal progress turn through the orchestrator. Direct Sidekick contact remains available when the user explicitly chooses it. A milestone, completed slice, or phase return is a checkpoint.
4. When a PR's planned development and fitting proof are complete, the orchestrator assesses that PR before its independent review. Inspect its current diff and actual proof against the original need, accepted design, its plan, node, base, and scope. Confirm required behavior is demonstrated through the right observation seams, no required work or proof is missing, boundaries and names match the design, and unnecessary complexity or unplanned compatibility machinery was not introduced. Cross-PR interaction is proved at the breakdown's integration gates (step 9), not in this per-PR assessment. Unproven work returns to the responsible implementer for fresh affected proof. A mental-model break, public-contract change, owner decision, or plan defect stops dependent work and returns to its semantic owner. IF an implementer or reviewer reports a design break, load `../../shared-references/owner-decision-brief.md` and return the brief. Only a source-backed accepted assessment commissions that PR's independent 🔎 Review Sidekick through `manage-agents`, using its verified `<emoji> <role> · <purpose>` title or reporting the title capability gap.

   Return a concise source-backed assessment decision that makes the substantive inspection and outcome clear without imposing a reporting schema. A missing label alone does not invalidate adequate evidence; an assessment supported only by the implementer's summary does not authorize review.
5. Each independent PR gets its own different-lineage 🔎 Review Sidekick with no author history. A stack gets one Review Sidekick relationship that reviews each layer's diff against its parent and that layer's plan, in layer order. The Review Sidekick runs `implementation-review` for general-domain work or the `skills-creation` implementation-review stage for a composed runtime skill package, on exactly one PR or one stack layer. It owns detailed source reading, lane reduction, and its review result. The orchestrator checks findings against cited evidence, resolves scope or design disputes, and returns accepted implementation corrections to that PR's implementer.
6. Main hands the corrected code and fresh affected proof to the same 🔎 Review Sidekick for that PR or stack, which checks them; the implementer does not contact the reviewer directly, and a reviewer is never reused across independent PRs. It refreshes affected coverage and applies the convergence rule in `implementation-review`'s `references/finding-and-reduction.md` to that PR or stack layer. Contextual design feedback remains separate from independent review.
7. Repeat correction, proof, and review while accepted findings remain for that PR or layer. IF the review returns `not-converging`, load `../../shared-references/owner-decision-brief.md` and return a brief of what keeps failing and why.
8. When a PR's review is ready, assign `implementation-pr-wrapup` for that PR to an 🔧 Operator or its assigned implementation Sidekick and require current PR gate evidence back to Main for verification. A stack wraps up from its lowest layer up. Operators own separately assigned Git, PR, and blocking-watch routines; wait for their notifications or authorized wakes through `manage-agents`, never by model polling. Stop at PR-ready and unmerged by default. Pass through explicit merge authority only after readiness.
9. After the PRs an integration gate names are PR-ready, Main runs that gate's proof and records in the trace the exact PR heads it tested together. A change the gate discovers routes through Main to the affected PR's Sidekick and reviewer. Per-PR readiness is never reported as delivery readiness before the named gates pass.

Record consequential decisions, accepted or rejected findings, corrections, proof outcomes, gate results, any missing-history baseline, blockers, and terminal results through `practices-show-me-your-work`. Keep logging a companion to delivery: do not create another lifecycle ledger, copied receipt store, counter protocol, or result replay mechanism.

If prior review evidence for a PR or stack layer is unavailable, inspect that unit's current source and proof boundary, record what is missing, and route an ordinary review; the current review sets that unit's convergence baseline.

## Boundaries and Finish

- The orchestrator remains the default user conversation and owns governing design, the breakdown and PR plans (authored with `plan-implementation` in Main's own session, outside this skill), dependencies, stack sequencing, integration gates, per-PR assessment, acceptance, source-backed disposition, routing, and the delivery terminal. Each implementation 🐒 Sidekick directly owns bounded implementation, fitting proof, corrections, and routine mechanics for its one PR; the user may explicitly choose direct contact with it inside that scope. Each Review Sidekick owns independent review findings and coverage for its PR, or for each layer of its stack. The user owns material design decisions and phase gates. PR wrap-up owns PR gate inspection.
- Verify producer results proportionally. Current scope, source, outcome, evidence, and applicable stop conditions matter; a missing label alone does not invalidate a clear result. Require exact identity when it changes correctness, including the breakdown, node, base, canonical plan, reviewed diff or PR head, and source-bound proof.
- Shared work updates follow the tracker within task authority. Other external tracking remains separately authorized work and proves no delivery gate.
- On every terminal response, record the actual `complete | partial | blocked | stopped` outcome and continuation context through the tracker. Nested agents checkpoint without resolving the outer thread. Only the responsible whole-work agent checks current history and whole-work completion before resolution; render a view when requested or substantial synthesis is needed.

Open stand-ins keep a PR from `pr-ready` unless the owner accepts them, and the final report lists every open stand-in as unverified.

Completion: every material phase required by the requested terminal is currently verified (for `plan-only`, a ready breakdown and plans; for `pr-ready-unmerged`, admitted plans, implementation with fitting proof for every PR, a ready review for every independent PR and every stack layer with accepted corrections, PR readiness for every PR, and every named integration gate passed on recorded heads), or the response names the exact decision or blocker. No phase boundary, missing label, logging failure, implied merge, or continuing after `not-converging` silently changes that result.
