## Problem and Evidence

Observed failures (user-reported across sessions; wording gaps verified against current files on `origin/master` at `3f3dfb6`):

1. **Reviewers go off the rails.** Models accept or invent findings that are over-engineered or out of scope — the "unrequested security harness subsystem" pattern — instead of defending the requirements and staying on the specification rails. Evidence: `review-implementation/references/finding-and-reduction.md` has zero goal-boundary, scope-effect, deletion-test, or over-engineering language; its dispositions test only "does the source prove the defect," never "is this correction in scope." `spec-program-review` carries rails in `references/reviewing-common-method.md` (accepted-requirements verification, deletion-first, no scope expansion — loaded by every lane) and in parent reduction (SKILL.md step 9); the gap there is consolidation and strengthening plus the implementation-side over-delivery check, not first-time propagation.
2. **Reviewers do not read whole files.** `review-implementation/references/reviewing-implementation.md:11` says "completely enough to establish its identity and scope," which licenses partial reads. `spec-program-review/references/reviewing-common-method.md` has the strong rule ("read every target file completely") but no completion criterion demands legwork only a full read can produce. Constraint: reading inventories (receipts, digests, line counts, chunk reports) were deliberately banned (commit `7c47c71`); enforcement must come from legwork-demanding completion criteria instead.
3. **Monolithic or partial-information review.** `review-implementation` dispatches one complete reviewer for everything; the retired `implementation-review-swarm` dispatched a fixed parallel lane roster with nobody deciding chunking, so every lane got partial information. Neither shape has a coordinator that views the whole change, decides the chunking, and hands each reviewer a deliberately overlapping packet.
4. **Findings rubber-stamped.** Parent acceptance sometimes takes reviewer output at face value instead of verifying against requirements, specification, and program design (user-reported; evidenced for implementation review by the missing re-anchor gate in `finding-and-reduction.md`).
5. **Naming inconsistency.** `review-implementation` breaks the namespace-first family (`implementation-handoff`, `implementation-pr-wrapup`). User-directed rename.

## Success Definition

After all runs land: when reviewing an implementation or a design, the parent agent acts as review coordinator — it reads the governing sources and the change completely, composes a review DAG whose parallel parts fan out and whose dependent parts run in sequence, hands each reviewer subagent a complete packet with the shared conceptual context recorded by the governing basis (per D3) plus its chunk with deliberate overlap, and reduces all receipts itself. Every accepted finding is anchored to a confirmed requirement, Specification obligation, Program Design element, or confirmed goal-boundary field; findings that add unrequested subsystems, expand scope, or weaken requirements are rejected with evidence or returned to the user as `decision-needed`; a mental-model break returns to the user instead of being pushed through. Reviewers read every loaded target file completely. In implementation review a proof-challenge lane with bounded execution authority verifies or challenges claimed proof; in design review that lane is composed only when the design cites executable proof claims (D16). The skill is named `implementation-review`.

| # | Decision | Rationale |
