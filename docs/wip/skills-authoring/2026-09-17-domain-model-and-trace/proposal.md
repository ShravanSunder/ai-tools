## Success definition

Given a Specification for a change in a TypeScript monorepo where at least one event or message crosses a process or service boundary, an agent following the design skills — unprompted, with no user correction — produces:

1. a Specification whose entities are defined with stable `E` identifiers (term, identity rule, relationships, invariants, observable states) and whose every obligation is written over defined entities (R1);
2. a Program Design whose first structural stage after direction selection binds each spec entity to a semantic owner (component), an owning package (`new | modified | existing`), a schema/type home, a wire shape for every boundary crossing (name, fields, nullability, discriminant), and a `persisted | derived | cached` disposition — expressed in the repository's declared type conventions when present; result and decision contracts are closed variants with bounded reason sets (R2);
3. one durable trace table in the Program Design, constructed by one reference, with one row per obligation: `R` · `E` · semantic owner · interface/contract · data shape and home · state · failure handling · proof seam — every empty cell marked `gap`; the returned coverage disposition is derived from this table (R2);
4. a turn that ends with terminal `decision-needed` (decision class `structural-realization confirmation`) after showing the owner the binding table, trace table, new components and contracts, one entry-to-effect path, and complexity spent; review dispatch happens only on a later turn after the owner's reply; the gate and the Required Views table sit before `## Workflow` in `program-design/SKILL.md` (R2);
5. a three-artifact review whose lane receipt carries `structural-realization confirmation: inspected | missing` and whose parent result is `decision-needed` when missing; the review checks the trace table row by row and term consistency across all three artifacts (R3);
6. an orchestrator that routes to review only on `locally-ready` plus confirmation and refuses `ready` without it (R4).

Proof: the pressure scenarios named per run go RED against the current skills and GREEN after each run lands, with the reproduction class of each scenario recorded before authoring.
